What Temporal does

Temporal keeps a backend process moving through failures. Your code sets the order of work. Temporal stores a history of key events: a workflow started, an activity completed, a timer fired. A worker uses that history to rebuild workflow state after a restart.

The local demo models an order for one user: validate user → reserve item → take payment → pack box → send order. These business actions are simulated; they do not charge money, reserve stock, or send parcels.

Connect another software system

The reusable service uses /api/v1/jobs. Any language can call its JSON API. Each job contains one to twenty named tasks. The operator registers the task URLs and rules; callers cannot choose arbitrary URLs or credentials. Software without HTTP can use a small HTTP adapter.

Production call flow
Your backend → HTTPS gateway → JWT check → Jobs API → Temporal → worker → named HTTPS adapter
The adapter saves its business change and idempotency key. Temporal saves the result. The backend reads job status or one page of events.
  1. Identify the caller: validate JWT issuer, audience, and read/write scopes. Derive the owner on the server; do not trust a caller-supplied owner ID.
  2. Accept one job: use a stable business job ID. Another job ID creates another job for that caller. A duplicate retained job ID returns a conflict.
  3. Do each task: send the same idempotency key on every retry. The adapter must enforce it with its saved result. Logging a key does not prevent duplicate writes.
  4. Save progress: Temporal records task results and durable waits. Production waits default to zero; the local visual demo keeps twenty seconds.
  5. Handle failure or cancellation: run configured undo tasks in reverse order. Register undo before execute because a write can succeed even when its reply is lost. Undo must be safe if execute never happened or is still in flight.
  6. Escalate uncertainty: failed undo or an explicitly irreversible action can need manual review. Read the business result as well as Temporal execution status. Force termination bypasses workflow cleanup.

Only the local profile serves these pages and crash controls. The production profile requires JWT checks and mTLS to Temporal, separates management endpoints, and rejects unsafe configuration. The production Kubernetes template uses two API pods and two workers, mounted settings, non-root containers, and disruption/network boundaries. Your platform still supplies the real adapters, identity provider, TLS ingress, Temporal storage, backup system, and alerts.

Local demo architecture and direction of calls

Local demo run, step by step

  1. The API asks Temporal to start a workflow. Temporal saves its inputs and schedules a workflow task.
  2. A worker polls for work. The task carries history needed to run the workflow code.
  3. Workflow code requests an activity. The worker sends commands to Temporal; Temporal records them and schedules the activity task.
  4. A worker receives the activity, runs it, and reports the result. Temporal records a successful result before the workflow can use it.
  5. The workflow starts a durable wait: 20 seconds by default, after each simulated three-second activity. This is a delay between actions, not activity processing time. No worker thread needs to sleep for that timer.
  6. When the timer expires, Temporal records it and schedules more workflow work. The five-step run finishes after the final wait.

The task queue is handled by Temporal. It does not need a separate scheduler pod. Task execution reference.

What a crash changes

The crash button exits the worker process. Kubernetes usually restarts its container inside the same pod, so the pod name can stay the same while its restart count rises. Deleting the pod creates a replacement pod with a new name.

On recovery, a worker replays workflow code against recorded history to rebuild local variables. It reuses recorded activity results and elapsed timers. It then makes new progress. This is not a saved Java memory snapshot. If no worker is available, tasks wait; timers can still expire on the Temporal Service. Event history reference.

An activity may run again if its worker crashes before its result is recorded. Its current timeout is 20 seconds, with at most five attempts. A real payment or stock write needs an idempotency key enforced by the destination, so a retry cannot apply the same change twice. Recovery may wait for a task timeout or retry delay. Retries and recovery reference.

How to read the operations page

  • Temporal events: saved scheduling, task, activity, and timer events. They stay readable through worker downtime. They do not record every line of code or every activity retry attempt.
  • Pod status and events: Kubernetes observations, including container state and restart count. Kubernetes events have finite retention; they are not a permanent audit log.
  • UI observations: polling requests, HTTP errors, and button responses. A crash request being accepted does not prove that a restart has finished.
  • Worker logs and metrics: startup and activity details appear in container logs. Idle queue polls are not workflow history events; use SDK metrics for poll counts and latency.

What each order step means

StepPurpose in a real systemIf it fails
1. Validate userCheck the user can order.Retry temporary errors; reject invalid users.
2. Reserve itemHold stock for this order.Retry safely; report sold-out items.
3. Take paymentAsk a payment provider to charge once.Use an idempotency key; release stock if payment fails.
4. Pack boxAsk the warehouse to prepare the parcel.Retry the same packing job.
5. Send orderAsk a courier to collect the parcel.Retry the same shipment request.

These are intended business meanings in the local demo. Its old workflow stays compatible with saved demo histories and does not perform real business calls. New integrations use the reusable job workflow and configured execute/undo adapters. The provider must implement real stock release, refund, and shipment rules; the service cannot invent safe business rules.

Deployment scope

UserOrderWorkflowImpl sets the flow. UserOrderActivitiesImpl simulates work. WorkerModeRunner registers and starts workers. DemoController starts and observes runs. HistoryStatus builds progress from saved Temporal events, without requiring a live worker.

The local stack is a recovery environment with simulated business actions and one worker to make downtime visible. The separate production baseline adds secure API/configuration and deployment boundaries. Go-live still requires your actual adapter contracts, secrets, ingress, Temporal deployment, backup restoration, load checks, and previous-release replay checks. A new database volume does not copy data from an existing unmounted database; migrate existing data before replacing that pod.

For safe upgrades, keep v1 workflow code and its queue available for old runs. An incompatible flow needs a new contract or a tested Temporal versioning plan. Passing a replay test built from the same source is not proof that every previous production run is compatible. Worker release guidance.
